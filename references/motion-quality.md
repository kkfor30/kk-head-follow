# 连续性排查与交付

用于新素材标定、接缝修复和用户反馈卡顿、回摆、重影时。先保留可复现的旧版本，记录实际加载的图集版本，再改动。不要把整个视频转过一圈等同于可用的闭合方向环。

## 先定位问题在哪一层

按同一姿态比较原视频、编译后的原生帧、程序合成帧、网页叠加结果。用源帧号或时间关联，不能只凭截图断定是视频模型的问题；截图也不足以证明缺陷只有一帧。

| 现象 | 区分方法 | 优先处理 |
| --- | --- | --- |
| 只有左右摇摆 | 查看鼻尖、双颊、耳朵比例和下巴角度 | 区分侧倾、平移与真实转脸和抬低头；只有缺少所需动作才考虑生成 |
| 转脸但眼睛看镜头 | 放大左右、上下及中间段的双眼 | 头部与视线分别验收，重新标定不能创造缺失的眼神 |
| 顶部先反摆再转动 | 连看接缝前后多帧，比较转脸趋势，而非只比首尾相似度 | 去除回正、反向段，重选端点和方向锚点；保留自然侧倾，不要求所有像素单调移动 |
| 顶部停顿或突然跳转 | 先确认图集本身是否停留/跳变，再检查实际取帧路线 | 裁剪停段或重标定；检查角度跨界是否走短弧、是否误入回正区，不用更大阻尼掩盖 |
| 旧头形描边 | 对照静态底图的旧发际线与背景处理结果 | 检查浅色抗锯齿像素是否被回填、羽化是否露出旧头；按背景路线处理 |
| 耳后灰影、眼镜重影 | 原生帧干净但合成帧异常，则先查插帧；原生帧也异常则向上追溯 | 检查遮挡变化、光流错误、两端轮廓混合；不能把它当背景描边一律扩大羽化 |
| 网页与检查图不一致 | 核对服务目录、当前清单及图集版本、加载失败与缓存 | 先确认用户看到的资源，再评价算法；备用端口不等于原端口已经更新 |
| 同方向近远移动，转头幅度完全一样 | 核对是否仅按 pointerAngle 取帧 | 当前单环的能力边界，不能用阻尼补上二维幅度 |
| 原图看镜头，进入/退出时突然换眼神或表情 | 对照 neutral 与实际进入/退出源帧 | 按 gaze-and-rest.md 核对真实过渡；静态回退和两脸叠化不是自然回正 |

## 修复的顺序与边界

1. 优先使用原视频中方向正确的连续段，排除进入、回正、反向和停留段。裁剪之后重新计算帧来源及八方向锚点，不照搬旧索引。
2. 同时检查端点姿态、接缝两侧运动趋势和速度。相貌接近、像素差小，仍可能产生回摆或停顿。不能只选择最相似两帧闭环。
3. 原生段仍有小缺口时，可按用户目标试验程序插帧；它是可选修复，不是默认生产步骤。先做短段对照，不批量覆盖已可用素材。
4. 插帧尤其容易在头发、耳朵、眼镜、下颌和颈部的显露/遮挡处失败。对齐后的双向混合仍会重影；平滑光流也可能损失细节。不得把某个滤波参数推广为通用修复。
5. 若仅少数合成帧有问题，可尝试剔除或换用更近的可靠端点，但必须重新检查跨越被删帧后的跳变。增加帧数、重复帧、透明度叠化不等于恢复真实动作。
6. 程序修复仍有明显缺陷时，保留明确标注的预览或退回较可靠版本，说明未解决项；缺少动作且现有素材无法修复时才讨论补段或完整重做。付费生成沿用已有授权预算，不自动追加。

## 每次修改后验证什么

Agent 负责第一轮检查和修复，用户负责最终体验确认。先运行 `review_head_atlas.py` 生成证据包，再实际查看，不得把“报告已生成”写成“视觉已通过”。报告包含全部帧的原场景局部合成、所有合成帧及其邻帧、正反向帧序列预览、异常像素差提示和清单哈希。它不会自动识别所有残影，也不执行真实鼠标控制器；有浏览器授权时再检查交互，没有可用浏览器时明确这一项未测，不阻止离线检查和修复。

执行闭环：基本动作可用性核验 → 程序编译与合成 → 生成并查看证据 → 定位到帧和区域 → 局部修复 → 同范围复查并查新缺陷。原生动作可用时优先完成这个闭环，避免反复付费生成。修复若引入拉伸、黑色残片或更大的跳变，撤回该候选，保留证据并换处理方式，不要求用户逐个试错。只有缺失真实动作、身份破坏等现有程序无法可靠恢复的问题才考虑新生成。

- **原生与合成帧**：逐帧检查整个修改段和两侧邻帧。`inspect_atlas_seams.py` 用来找像素异常及拼接点，不会证明眼神、运动趋势或遮挡正确。合成段可能内部有坏帧，不能只看首尾四帧。
- **合成到原场景**：检查新旧轮廓覆盖、颈部连接、羽化和前景遮挡。独立头部接触表通过，不代表页面叠加通过。
- **交互轨迹**：按用户授权由 Agent 或用户测试顺/逆时针完整绕行、顶部双向缓慢跨越、快速反向、停留于过渡区、进入/离开回正区。停住时也不能留下重影。检查资源加载与帧变化，再区分性能卡顿和素材停顿。
- **证据状态**：分别记录生成完成、方向覆盖、眼神协调、接缝、合成边缘、页面接入及用户验收。未知写待确认；构建、哈希和图集校验通过不代表视觉通过。

项目记录至少包含：输入和原视频版本、实际请求（如有）、选用源帧范围、方向锚点、合成帧来源、修改前后证据、当前预览地址与已知缺陷。原生素材与合成素材分别保存，避免覆盖后无法追查。

## 沉淀到 Skill 的证据要求

可复用的是诊断方法和经验证的处理条件，不是某个项目的帧号、裁剪坐标、人物特征或本地路径。用户认可整体改善但仍反馈重影时，只能记录部分改善；不要把该插帧算法包装成已经验证的默认能力。示例素材须明确用途、可分发条件和局限，不能让流程依赖作者的私人资源。
