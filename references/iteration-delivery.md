# 首轮候选与用户驱动迭代

目标是先在用户要求的真实场景中提供诚实、可体验的候选，再根据用户反馈修复。首次生成不保证完整或完美；两三轮是可接受的迭代空间，不是默认生成次数或成功保证。

## 首轮

1. 生成前明确实际输入姿态、动作路线、生成构图和最终合成方式。全人物分层不等于必须全身生成；局部输入也不意味着可以直接拼回旧身体。任何裁切必须保留坐标和头颈运动余量。本规则不宣称绿幕、近景或某种首尾方案必然成功。
2. 默认仅一次 5 秒/768p 试片，用户明确的其他范围优先。生成后先检查全片方向覆盖、身份、明显变形、持续闭眼和表情变化，再投入插帧、图集编译与细节修复。不要到第二版图集才发现母版缺失半圈。
3. 明确缺陷后先做一轮针对性的程序处理，比较原件与候选。只有有证据表明改善且下一步目标具体时才继续；同一缺陷连续两次程序处理无改善或引入更严重问题，保留较好版本并交付问题说明，不循环试算法。此停止条件不限制修复代码错误、缺文件等可确定解决的问题。
4. 交付下面适用的候选，说明实际完成范围、残留缺陷、生成次数和下一步。不得把“全部工程检查通过”作为所有预览交付的前提，也不得宣称候选已通过正式验收。

## 候选分级

| 源素材 | 交付方式 |
|---|---|
| 方向环基本完整，存在边缘、节奏或小接缝缺陷 | 结构校验后，在真实背景和布局的独立候选页使用 diagnosticPreview:true 提供鼠标体验；显式标注缺陷，并保留静态对比 |
| 仅部分连续真实方向可用 | 有限方向预览，标明有效方向区间；区间外回静态或保持边界。不得把半圈拉成整圈、伪造八个锚点或循环穿过缺口 |
| 主要歪头、方向不可标定、严重变形 | 真实场景合成播放与静态对比，明确不是方向跟随；不强行把视频时间映射为鼠标方向 |

当前标准运行时/编译器要求八个真实方向锚点，尚不支持有限方向模式。部分覆盖时，只有能可靠建立区间映射的独立预览才采用有限方向；否则交付合成播放，并说明未实现有限方向交互。不要降低标准清单约束来伪装支持。

原始母版、源帧、处理候选与已验收版本分开保存。用户要求启用候选时可显式提供候选入口，但不能改写质量记录为 ready。正式版本仍按 runtime.md 与 repair-and-review.md 检查。不能浏览器验证时如实记录，完成可执行的离线检查并提供入口，不声称体验通过。

## 后续修复与生成预算

- 用户指出问题后，先定位源动作、映射、合成或运行性能；程序可修则直接处理，不反复索要已具备的授权。
- “这里卡顿/有残影”本身不等于允许新增付费视频。缺失源动作需要生成时，先说明要补什么、使用什么首尾、拟新增次数与时长，再按已有明确授权执行；没有授权才询问。用户明确要求重新生成则不重复确认。
- 同一项目、同一效果任务使用唯一的共享预算文件，默认 build/generation-budget.json。pilot、repair、重试都累计；子目录不能自建预算重新获得次数。已有任务沿用原预算，不迁移清零。
- 后续获授权时，在同一预算保留 attempts，记录用户授权内容及本轮用途，增加相应 maxSubmissions、maxTotalSeconds 等限制，并记录 limits.changeReason。授权一条补片不等于授权无限补片。查询已有 job 不算新生成。
- 启动前检查该任务已存在的预算和 submission.json；若此前分散记账，先汇总核对，不能把旧次数视为零。目前脚本只约束传入预算文件，跨文件预算归属仍依赖 Agent 遵守本规则；不得宣称程序已全局阻止绕过。
- 补片先验动作与表情，再拼接。接点绑定实际参考帧，检查两侧多帧运动趋势；复制第一帧到末尾不是闭环通过证据。每轮修复复查目标缺陷及新增副作用，不为未变素材重复整套无关检查。

完整交付路径是“首轮有限成本候选 → 用户反馈 → 定点程序修复或获授权的新生成 → 同场景对照”。缺陷记录和静态回退是保护措施，不替代本来能够完成的候选交付。
